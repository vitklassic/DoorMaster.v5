# DoorMaster — Технические стандарты (ТС)

Обязательны для всех ролей. Изменения — через архитектора (Kimi Work) с обновлением этого файла.

## 1. Единицы измерения
Все линейные размеры хранятся и передаются в **миллиметрах, целые числа** (`*_mm integer`). В UI — подпись «мм». Недопустимы см/м/дробные мм в БД.

## 2. Номер квартиры
Только числовая клавиатура: `keyboardType="numeric"` (уже соблюдено в `ObjectForm`). В БД — текстовое поле `apartment` (лидирующие нули допустимы на уровне отображения).

## 3. Мультитенантность и RLS
Каждая бизнес-таблица обязана изолироваться по `company_id = current_company_id()` (прямо или через родительскую запись). Клиент никогда не доверяет своим данным о компании — фильтрация и авторизация только на сервере. Новые таблицы — только с миграцией + RLS-политиками + комментарием в шапке миграции.

## 4. Схема открывания двери
Подпись **«коридор» (`corridor`)** обозначает место наблюдателя: монтажник стоит в коридоре лицом к проёму. Это не план квартиры и не координатная привязка размеров. «На себя» — открывание в коридор, «от себя» — в комнату; «влево/вправо» — сторона петель при взгляде из коридора. Визуализация — через `schemaGeometry` + `OpeningSchema` (SVG), тот же рендерер используется в PDF. Новые геометрические сущности должны переиспользовать эту библиотеку.

## 5. Статусная модель и версии замера

**Новый обязательный стандарт после повторного теста 2026-11-06:** [SPEC-post-test-rework](SPEC-post-test-rework.md), T12. До реализации T12 в коде ещё действует прежняя четырёхстатусная модель.

- Только `active` («В работе», жёлтый), `done` («Готов», зелёный), `archived` («Архив», серый). `draft` удаляется; существующие черновики мигрируют в `active`.
- Менеджер: `active → done → archived`, а также `archived → active`.
- Монтажник не выбирает статус вручную: до нажатия «Доработать замер» редактирование закрыто; при доработке рабочая версия получает `active`.
- «Оригинал / Копия» — отдельная пометка версии, не статус. Оригинал нельзя удалить или изменить; его можно архивировать и можно дополнять новыми проёмами. Редактирование/удаление содержимого выполняется через связанную копию, оригинал остаётся нетронутым.
- Владелец, переходы и сохранность оригинала обязательно контролируются сервером (RLS/RPC), не только интерфейсом.

## 6. Роли и владение данными
`installer` — создание и доработка **только собственных** замеров (`measurements.user_id = auth.uid()`). `manager` — замеры всех монтажников своей компании, инвайты и переходы статусов по ТЗ. Проёмы, фото и realtime наследуют те же ограничения. Разрешения — в `lib/auth/roles.ts` (`ROLE_PERMISSIONS`), экраны гардируются ролью, а доступ к данным дополнительно проверяется RLS. **Запрещены** debug-переопределения ролей на клиенте (урок C1 из аудита).

## 7. Кроссплатформенность
Цель — Expo Go на Android/iOS. Запрещены web-only API в общем коде (`window`, `document`, `localStorage`). Web-специфику прятать за `Platform.OS === 'web'` с кроссплатформенной заменой (expo-print, expo-image-picker, expo-file-system, AsyncStorage).

## 8. Ошибки и диагностика
- Все действия через `runAction`-обертку контекста: пользователю — понятное сообщение, состояние экрана не ломается.
- В обычном/production-режиме сообщения — на русском, без внутренних технических деталей.
- В тестовом режиме T10 полные исходные ошибки, стек/`cause`, действие, платформа и сетевые коды доступны с первого запуска; тестовый CMD включает этот режим автоматически.
- Секреты, пароли, токены и приватные подписанные URL никогда не попадают в журнал. Подробности — [SPEC-post-test-rework](SPEC-post-test-rework.md), T10.

## 9. Код-стайл
Prettier (`.prettierrc`), строгий TypeScript (`tsc --noEmit` без ошибок — обязателен перед сдачей). Алиас `@/` — единственный способ импорта вне относительных путей текущего модуля.
