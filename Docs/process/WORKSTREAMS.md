# DoorMaster — направления и границы работ

Обновлено: 2026-11-06.

## Основная модель

`Shell`, `Core` и `Commercial` — направления разработки, а не три постоянные Git-ветки. Источник истины — `main`. Для отдельной согласованной задачи допускаются короткие ветки `feat/shell-…`, `feat/core-…`, `feat/commercial-…`, которые после приёмки возвращаются в `main`.

Роль можно выполнять последовательно одним агентом. Дополнительные агенты нужны только по явной просьбе заказчика; одновременная правка одного файла разными исполнителями запрещена.

## Три направления

| Направление | Основная роль | Что входит | Что запрещено без отдельного согласования |
| --- | --- | --- | --- |
| **Shell — оболочка** | Creative / UI | UX/UI, тема, экраны, стили, тексты, клавиатура, компактность, адаптация | Менять backend, схему БД, права и бизнес-логику |
| **Core — рабочая логика** | Кодер | Auth, замеры и проёмы, владение данными, статусы, оригинал/копия, realtime на клиенте, фото, PDF, валидация | Менять миграции, RLS, RPC и Storage без Интегратора |
| **Commercial — коммерческий контур** | Commercial | Компании, тарифы, лимиты, оплата, onboarding, администрирование, поддержка, аудит | Добавлять биллинг и платёжные интеграции в код до стабилизации Core и отдельного ТЗ |

Commercial сейчас развивается только документами. Это направление не должно тормозить текущие исправления приложения.

## Сквозные роли

- **Архитектор** — координирует направления, пишет и уточняет ТЗ, разрешает пересечения, принимает результат вместе с QA. Работает с `Docs/`, код приложения не меняет.
- **Интегратор** — единственный владелец миграций, RLS, RPC, Storage и серверной настройки realtime. Обслуживает все три направления.
- **QA** — проверяет каждую партию по тест-плану, фиксирует доказательства и регрессии. Не исправляет production-код незаметно вместо ответственной роли.

## Зоны ответственности

| Роль | Разрешённые зоны | Ограничение |
| --- | --- | --- |
| Creative / UI | `app/`, `components/`, стили и тексты в рамках утверждённой UI-задачи | Только представление и взаимодействие; общие экраны заранее согласовать с Кодером |
| Кодер | `app/`, `components/`, `lib/measurements/`, клиентская часть `lib/backend/`, фото/PDF и валидация | Не менять схему БД и серверную безопасность |
| Интегратор | `supabase/migrations/`, RLS, RPC, Storage, realtime; серверные контракты | Изменения `lib/backend/` выполнять совместно с Кодером, не переписывая чужую работу |
| Commercial | `Docs/design/`, `Docs/process/` и отдельное коммерческое ТЗ | До отдельного решения — без кода приложения |
| QA | Тест-планы, результаты проверок, диагностические артефакты | Не выдавать непроверенное за пройденное |
| Архитектор | `Docs/`, декомпозиция и приёмка | Не редактировать production-код |

## Правила пересечений

1. У задачи один ответственный исполнитель и один список файлов. Остальные роли подключаются только по явно обозначенному участку.
2. Перед правкой общего экрана или модуля ответственный объявляет затрагиваемые файлы. Параллельные правки этих файлов не начинаются.
3. Изменение данных, API, статусов или прав доступа требует актуализации ТЗ Архитектором; изменение БД выполняет Интегратор.
4. Shell может менять расположение и внешний вид существующих элементов, но не значения, переходы статусов, фильтрацию владельца и правила сохранения.
5. Любое изменение RLS проверяется позитивными и негативными сценариями. Клиентского фильтра для безопасности недостаточно.
6. После каждой партии: `typecheck` → проверка агентом → QA/ручная приёмка заказчиком. Только затем следующая партия.
7. Если два исправления подряд не помогли, работа останавливается: фиксируются полная ошибка, причина и следующий диагностический шаг.

## Текущая очередность

1. **Core + QA:** T10 — полная диагностика; T11/C20 — изоляция монтажников; T12 — статусы и оригинал/копия.
2. **Core + Shell + QA:** T13 — клавиатура и мастер; T14 — панель менеджера. Shell-задачи можно вести параллельно только при непересекающихся файлах.
3. **Commercial:** пока только требования и проектные документы. Код — после стабилизации Core и отдельного согласованного ТЗ.

| Задача | Ведущее направление | Обязательные роли |
| --- | --- | --- |
| T10 | Core | Кодер + QA |
| T11 / C20 | Core | Кодер + Интегратор + QA |
| T12 | Core | Архитектор + Кодер + Интегратор + QA |
| T13 | Core + Shell | Кодер + Creative / UI + QA |
| T14 | Core + Shell | Кодер + Creative / UI + QA |

## Скиллы

- Для Supabase использовать существующий проектный `supabase-dev`.
- **Core:** будущие `expo-crossplatform`, `backend-verification`, `doormaster-core` — кроссплатформенность, серверные проверки и правила DoorMaster.
- **QA:** будущие `session-handoff`, `backend-verification`, `expo-crossplatform`, `doormaster-test-checklist`.
- **Commercial:** будущие `billing-architecture`, `support-ops`; для БД и RLS — `supabase-dev`.
- Этот документ только фиксирует рекомендации: новые скиллы не устанавливать и не создавать без отдельной команды заказчика.

## Git

- Не разводить три долгоживущие версии приложения.
- Ветка создаётся под конкретную согласованную задачу и не живёт бесконечно.
- `commit`, `push` и удаление файлов — только по прямой команде заказчика.
