# DoorMaster — мастер-план от текущей точки до запуска

**Составлен:** 2026-11-06, роль Архитектор.
**Статус:** подтверждён заказчиком 2026-11-06. До подтверждения каждой конкретной задачи работа по ней не начинается.

## Подтверждённые продуктовые решения (2026-11-06)

1. **Один APK для всех компаний.** Брендинг (логотип, название, контакты, адрес) подгружается внутри приложения после входа и попадает в PDF-отчёты. Отдельные сборки APK под каждую компанию не делаем.
2. **Монтажникам не рассылаются персональные APK.** APK один, вход — по коду приглашения (уже работает). Опция на будущее: менеджер заранее создаёт карточку монтажника (имя/телефон), код привязывается к этой карточке.
3. **Цвета состояний у менеджера и в списках:** новая заявка, которую монтажник ещё не начал — оранжевый; замер «В работе» — жёлтый; «Готов» — зелёный; «Архив» — серый. Красный зарезервирован для реальных проблем (например, просроченная заявка).
4. **Заявка на замер** — это замер, созданный менеджером с заполненными данными объекта (название, адрес, телефон, заметка) и назначенный конкретному монтажнику. Монтажник видит его в своём списке, открывает и продолжает заполнение; дальше обычный сценарий. Отдельный тип документа не вводится.
5. **Панель владельца сервиса** (заказчик видит все компании: триал/оплачено, срок лицензии, блокировка) — скрытая роль в том же приложении или простая веб-страница. Отдельное приложение не делаем.
6. **Триал** — компания с тарифом «пробный» и датой окончания; изоляция компаний уже обеспечена RLS, отдельная инфраструктура для триалов не нужна. Логотип-заглушка «тут может быть ваш логотип» — в триал-оформлении.
7. **Уволенный монтажник** переводится в «архив»: исчезает с рабочего стола менеджера, его замеры остаются в архиве под его именем. Подробное ТЗ — позже.
9. **Магазины внутри компании (вилка А, утверждено):** пространство привязано к магазину (точке), менеджер назначается на магазин. Менеджер видит только замеры своего магазина, чужие магазины ему закрыты; пересылка замера между магазинами — отдельной кнопкой. Увольнение менеджера не трогает замеры: новый менеджер назначается на тот же магазин. Количество магазинов/рабочих мест ограничивается тарифом (связь с T17).
10. **Рабочие места магазина (уточнено 2026-11-06):** «рабочее место» — не сущность в базе, а просто аккаунт сотрудника, привязанный к магазину. Все сотрудники магазина — менеджеры с одинаковыми правами: видят все замеры и всех монтажников своего магазина одновременно. Один и тот же замер может быть открыт у нескольких сотрудников; просмотр свободный, изменения расходятся по realtime. Политика конфликтов — **мягкая, с предупреждением**: если коллега уже изменил замер (статус/назначение/поля), второй получает «замер изменён, обновите», и его правка не затирает чужую; жёсткой блокировки «редактирует Иван» нет. Проверка версии — на сервере (RPC/RLS), а не только на клиенте. Монтажник по-прежнему видит только свои замеры (T11).

## Подтверждённые UI-решения (Creative / UI, 2026-11-06)

1. **Цвет — не единственный маркер.** У каждого статуса и заявки, кроме цвета, есть текстовый ярлык или иконка («Новая», «В работе», «Готов») — для различимости при дальтонизме.
2. **Новая заявка у монтажника** показывается сверху списка, с ярлыком «Новая от менеджера» и заметным фоном; после открытия становится обычной строкой.
3. **Аватарки без фото:** автоматические кружки с инициалами и спокойным цветом; загрузка фото необязательна.
4. **Места логотипа компании:** экран входа, шапка приложения, шапка PDF-отчёта. От компании запрашивается PNG на прозрачном фоне (требования — в ТЗ брендинга).
5. **Триал-заглушка:** на месте логотипа аккуратная рамка «Здесь может быть ваш логотип».
6. **Карточки монтажников:** после создания карточки код показывается с кнопкой «Поделиться» (WhatsApp/Telegram/СМС), без ручного переписывания.
7. **Фильтр монтажников у менеджера:** горизонтальная прокручиваемая лента кружков «Все» + монтажники над списком; нажатие подсвечивает выбранного.

## Правила движения по плану

- Одна задача за раз; старт каждой — только после подтверждения заказчика.
- Каждая партия: `typecheck` → проверка агентом → QA → короткий ручной сценарий заказчика.
- Изменение плана — через обсуждение с Архитектором и фиксацию в этом файле.
