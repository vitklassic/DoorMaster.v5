## Уроки (что улучшить в следующих сессиях)

### 1. Миграции — сразу идемпотентные
Ошибка «column already exists» при повторном запуске T4 пугала заказчика. Правило: `ADD COLUMN IF NOT EXISTS`, `DROP POLICY IF EXISTS` перед CREATE, обёртки `DO $$ ... IF NOT EXISTS`. Идемпотентность — стандарт для всех новых миграций.

### 2. Файл для вставки — вместе с миграцией
Заказчик применяет миграции вручную через SQL Editor. Каждую новую миграцию сразу дублировать готовым файлом `tN-migration.sql` в корне workspace и напоминать: «запускать один раз».

### 3. Коммит в конце каждой партии
Долгая незакоммиченная работа — риск потери. Партия закрыта → сразу коммит (push — только по явному запросу заказчика).

### 4. Трение с подтверждениями доступа (главный UX-урок)
Заказчику не понравилось частое нажатие «разрешить» на операции с файлами. Это диалоги системы разрешений клиента Kimi Work, агент их не контролирует. Снижение трения:
   - **Со стороны заказчика:** в настройках клиента включить доверенную папку/авто-подтверждение для workspace `F:\Мой проект\DoorMastre` (или «всегда разрешать» при первом запросе доступа). Тогда диалоги перестанут появляться для этой папки.
   - **Со стороны архитектора:** заранее перечислять все нужные пути в первом же сообщении партии, минимизировать число обращений к файлам (батчинг), использовать git-команды пачками, а не по одной.
   - Сессионное правило: перед стартом партии агент просит разрешения на весь план работ одним списком.

### 5. Начало сессии
Агент первым делом читает `Docs/process/STATUS.md` — там точка ожидания и следующие шаги. Заказчику не нужно пересказывать контекст.

### 6. Тестирование
Заказчик предпочёл ручное тестирование без создания тестовых пользователей. План ручного теста есть в переписке и частично в TZ-T2; стоит вынести его в `Docs/process/TEST-PLAN.md` перед партией 3.

## 7. Анализ: какие скилы ускорили бы и удешевили работу

Отобрано по реальному трению этой сессии, по убыванию пользы:

1. **`supabase-dev`** (самый большой выигрыш). Сегодня 4 миграции заказчик вставлял вручную в SQL Editor, были путаницы («already exists», бакет не виден через anon). Скилл дал бы: генерацию идемпотентных миграций по шаблону, применение через CLI/Management API без участия заказчика, рецепты верификации живой БД (включая ловушку «private bucket = 404 для anon»), чек-лист настроек Auth. **Экономия: ~1 час ручной работы заказчика + снятие самого трения сессии.**
2. **`expo-crossplatform`** (для роли Кодер). Правила платформенного сплита (`*.web.ts`/`*.native.ts`), `npx expo install` для совместимости версий, ограничения Expo Go (что работает без dev build). Субагент заново выводил это из кода — скилл дал бы готовые шаблоны и сократил время и токены каждой партии.
3. **`session-handoff`** (для меня). Чек-лист начала/конца сессии: прочитать STATUS/ROADMAP, сверить git-статус и БД, обновить документы, коммит. Уже частично внедрено в процесс; скилл сделает это автоматическим и недорогим.
4. **`backend-verification`** (опционально). Скриптовая e2e-проверка через REST (регистрация → tenancy → RPC) до передачи заказчику. Заказчик отказался от неё в этот раз, но для регрессий после каждой партии она окупается.

**Эффект в целом:** меньше холодных стартов субагентов (дешевле), меньше ручных операций заказчика (быстрее), меньше ошибок идемпотентности (надёжнее).

## Дополнение после повторного теста 2026-11-06

### Что я делал не так

1. **Поздно включил полную диагностику.** Сначала заказчик несколько раз вручную повторял фото/PDF-сценарии, и только потом на экран начали выводиться настоящие `error.message`. Это была моя ошибка процесса: подробные ошибки должны быть включены до первого прогона.
2. **Проверял промежуточное состояние вместо конечного результата.** Фото видно до сохранения — ещё не означает, что JPEG загружен в Storage; PDF открыт — ещё не означает, что фото внутри и файл можно отправить. Нужна проверка всей цепочки и самого итогового файла.
3. **Слишком полагался на предположения о Expo Go.** Ограничения Hermes Blob, чтение `file://`, доступ Sharing к `cache/Print` выяснялись через повторные ошибки заказчика. Для нового платформенного пути сначала нужен минимальный технический тест и сверка возможностей конкретного SDK.
4. **Не проверил изоляцию вторым монтажником.** Первый тест доказал вход и роль, но не доказал, что монтажник видит только свои данные. Company-wide RLS ошибочно считалось достаточным. Негативный сценарий «А не видит Б» обязателен.
5. **Спешил закрывать задачи до подтверждения заказчика.** Неверно истолковал «коридор» и T8, а также попытался уточнять этажи через собственную логику. Сначала короткая формулировка требования заказчика, затем реализация; закрытие только после приёмки.
6. **Передавал заказчику слишком длинные ручные циклы.** Нужно самостоятельно прогонять web, типы, структуру SVG и доступные автоматические проверки, а на телефоне оставлять один компактный сценарий только для настоящего устройства.

### Что поможет в следующий раз

- **T10 — обязательный первый шаг:** `start-door-master-test.cmd` сразу включает полные ошибки и журналирование без секретов. Не начинать приёмку с общими фразами «ошибка загрузки».
- **Матрица результата:** для фото — локальный предпросмотр → реальные байты в Storage → отображение после Reload → присутствие в PDF; для PDF — предпросмотр → сохранённый файл → отправленный файл.
- **Два тестовых монтажника:** позитивные и негативные проверки владельца, RLS, realtime и Storage до передачи заказчику.
- **Полный перезапуск/жёсткое обновление перед выводами:** HMR может показывать старый вариант; сначала убедиться, что загружена новая сборка.
- **Маленькие партии с проверкой результата:** `typecheck` обязателен, но он не заменяет сценарий. Не делать несколько рискованных платформенных изменений одновременно без диагностики.
- **Правила в коде и на сервере одновременно:** скрытая кнопка не является защитой; статусы, оригинал/копия и владелец проверяются RPC/RLS.
- **Явная приёмка:** задача не закрывается по одному успешному типcheck или промежуточному изображению — только после проверки конечного поведения и, для визуальных задач, подтверждения заказчика.
