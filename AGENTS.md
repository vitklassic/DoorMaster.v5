# AGENTS.md — правила проекта DoorMaster

## Проект

DoorMaster — мобильное приложение на Android для замерщиков межкомнатных дверей с AI-функциями и личным кабинетом менеджера.
Ключевые функции: замер проёмов в миллиметрах, PDF-отчёты со схемами дверей и коридоров, фотофиксация.
Стек: Expo Go / React Native + TypeScript, Supabase (PostgreSQL) с RLS.
Текущее состояние: базовый сценарий работает на web и Android, Supabase подключён. Актуальная очередь переделки — T10–T14, она не считается выполненной без отдельной приёмки.
Подробности: `Docs/tech/ARCHITECTURE.md`, `Docs/design/TS.md`, актуальное ТЗ `Docs/design/SPEC-post-test-rework.md`.

## Кто я

Я новичок в разработке, программировать учусь по ходу дела. Объясняй коротко и простыми словами. Если просьба может сломать локальные данные, логику замера или безопасность RLS — предупреди до изменений.

## Как работать

- Отвечай коротко, просто и без лишней вежливости.
- Одна задача за раз. Для большой задачи сначала предложи план из 3–5 пунктов и дождись моего «да».
- Делай минимальное изменение, которое решает задачу. Не рефактори код вокруг без явной просьбы.
- Не добавляй новые экраны, библиотеки и npm-пакеты без моего согласия.
- Перед первой установкой или использованием новой сторонней программы объясни её назначение и спроси разрешение.
- Команды по возможности выполняй сам или через CMD-скрипт; не заставляй меня вручную вводить то, что можно автоматизировать.
- В тестовом режиме сразу включай полные ошибки без секретов. После изменения кода сообщи статус `typecheck` и сборки/запуска Expo одной строкой.
- Если исправление не помогло два раза подряд — остановись, опиши полную ошибку и предполагаемую причину; не повторяй правки вслепую.
- В конце задачи перечисли изменённые файлы и что мне проверить руками на телефоне в Expo Go.

## Роли и направления

`Shell`, `Core` и `Commercial` — направления работы, а не три постоянные Git-ветки. Подробности и границы: `Docs/process/WORKSTREAMS.md`.

### Протокол начала сессии

1. Прочитать `AGENTS.md`, затем `Docs/process/SESSION-CHECKLIST.md`.
2. Прочитать `STATUS` → `ROADMAP` → актуальное ТЗ → `TEST-PLAN` → `BACKLOG` → `RETRO` → `NOTEBOOK`.
3. Проверить `git status --short --branch`; существующие локальные изменения не удалять и не перезаписывать.
4. Объявить роль, направление, одну задачу и предполагаемые файлы. Только после этого начинать работу.

### Правила работы по ролям

- Архитектор пишет ТЗ и принимает результат, но production-код не меняет.
- Кодер отвечает за Core. Если нужна схема БД, RLS, RPC или Storage — останавливается и передаёт эту часть Интегратору.
- Creative / UI может менять только визуальную часть в рамках согласованной Shell-задачи; backend и бизнес-логику не трогает.
- Интегратор — единственный владелец миграций и серверной безопасности. Изменения `lib/backend/` согласует с Кодером.
- Commercial не добавляет биллинг и платёжный код до стабилизации Core и отдельного ТЗ.
- QA не выдаёт непроверенное за пройденное и не исправляет production-код незаметно вместо ответственной роли.
- Один файл одновременно меняет только один исполнитель. Дополнительные агенты подключаются только по моей явной просьбе.

## Git-модель

- Источник истины — `main`.
- Для согласованной задачи допускается короткая ветка `feat/shell-…`, `feat/core-…` или `feat/commercial-…`; долгоживущие разрозненные ветки не создавать.
- Сначала Core + QA (T10–T12), затем Core + Shell (T13–T14). Shell параллельно — только при непересекающихся файлах. Commercial пока документально.

## Экономия контекста

- Не читай `node_modules/`, `.expo/`, `build/`, `dist/`, `package-lock.json`.
- Не читай файл целиком, если нужно поправить одну функцию — найди её поиском.
- Показывай в ответах только изменённые куски кода, а не файлы целиком.

## Жёсткая архитектура DoorMaster — не нарушать

1. **Миллиметры:** высота, ширина и толщина стены обрабатываются, проверяются и сохраняются строго в `mm`. Никаких сантиметров.
2. **Числовой ввод:** `apartment` и телефоны клиентов используют `keyboardType="numeric"`.
3. **Безопасность:** у менеджера не проектировать кнопку «Удалить проём». Применять только разрешённую ТЗ архивацию/копирование. Данные защищаются RLS на уровне компании и владельца.
4. **Схема дверей:** каждый проём содержит логическую привязку схемы со стороны подписи «коридор» (`corridor`).
5. **Оригинал замера:** по T12 оригинал неизменяем и не удаляется; добавление проёма допускается без смены признака, редактирование или удаление — через копию.
6. **Язык:** имена файлов, компонентов, переменных и комментарии в коде — на английском. Общение со мной — на русском.

## Git и безопасность

- Не делай `commit`, `push` или удаление файлов без моей прямой команды.
- Не читай и не выводи `.env`, токены, пароли и ключи; не отправляй их в GitHub.
- После успешной проверки напомни о возможности коммита, но не выполняй его автоматически.
- Не завершай сессию самостоятельно — жди следующей задачи или моего явного завершения.
